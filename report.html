cuTile.jl on Triton

What it takes to retarget cuTile.jl from NVIDIA Tile IR to Triton, covering CUDA, AMD, and CPU · August 13–14, 2026

The port works. A prototype backend now consumes cuTile.jl's real front-end output (code_structured) and runs unmodified cuTile kernels — vadd, reductions, TF32 matmul, persistent softmax — through MLIR.jl → TTIR text → the stock triton pip wheel → CUDA.jl, without Reactant and without any Triton-specific native library. 10/10 correctness tests pass, including ragged sizes, padding modes, and while-loop persistence. On an H100, the Julia-emitted kernels match Python Triton's performance everywhere, and with the TMA descriptor lowering the fp16 matmul reaches 541 TFLOP/s — above both native tileiras (447) and cuBLAS (512).

The prototype backend

TritonEmitter.jl (~820 lines) walks cuTile.jl's post-optimization StructuredIRCode — the same IR the bytecode backend consumes — and builds TTIR through the generated tt builders. TritonRun.jl compiles via the wheel and launches through CUDA.jl with cuTile-style argument flattening (TileArray → ptr, sizes…, strides…). Kernels are written in the plain cuTile language; nothing kernel-side knows Triton exists.

The TMA / descriptor experiment

The emitter now has a second view lowering: when a PartitionView is descriptor-legal (2-D, unit-stride inner dim per ArraySpec, box dims ≤ 256, padding TMA can honor — zero-fill covers Zero/Undetermined, NegInf falls back), it emits tt.make_tensor_descriptor + tt.descriptor_load/store, mirroring Python's tl.make_tensor_descriptor exactly (i32 shapes, i64 strides, literal-1 inner stride, element offsets). The launcher allocates the TMA workspace the way Python's driver does (grid volume × global_scratch_size, 128-aligned). Same kernel source, same correctness suite: all 10 tests pass on both lowerings.

  • fp16 is the headline: descriptors are worth 4.8× (114 → 541 TF), and the cuTile-language kernel through Triton beats both native tileiras (447) and cuBLAS f16 (512) on H100. At tileiras' own tile config it ties (453 vs 447).
  • tf32 is a Triton backend gap, not an emitter gap: Python's own descriptor matmul lands at the same 69 TF (parity again), and the tt.warp_specialize loop attribute doesn't move it. Decisively: Triton's official TMA examples (python/tutorials/09-persistent-matmul.py) are hard-coded fp16/fp8-only (dtype = tl.float8e4nv if FP8_OUTPUT else tl.float16) — no tf32 descriptor matmul exists upstream at all. Keep pointer+mask (or tileiras) for f32 GEMM until upstream catches up.
  • Validated against the canonical kernel: tutorial 09's matmul_kernel_tma (group swizzle, K-innermost operands, b.T, optional warp-spec), run at the same config on the same arrays: 529.6 TF (536 with warp-spec) vs our 541.5 — the cuTile-derived lowering slightly outperforms Triton's own reference, on natural column-major layouts where the tutorial requires a pre-transposed A.
  • Consequence for the backend design: the descriptor-vs-pointer decision is a per-specialization compile-time choice (different TTIR), keyed on the same ArraySpec machinery cuTile already specializes on — plus a dtype heuristic (TMA on for f16/f8, off for tf32 on this Triton version). The "automatic TMA" that tileiras does moves into the emitter, where the view carries all the information needed; the cuTile kernel source is unchanged either way.
  • Device-side descriptor cost, measured: an isolated micro-benchmark (descriptor-creation-only vs empty kernel) puts it at ~5.3ns per descriptor per CTA, scaling linearly with grid size — the UTMACCTL.IV tensormap-cache invalidates serialize across CTAs instead of amortizing over SMs (SASS prologue: ~282 instructions, shared-memory descriptor assembly, async fences). For the 4096³ matmul (512 CTAs, 4 descriptors, 254µs) that's ~12µs ≈ 4–5% missing perf — host-side descriptors would put the estimate at ~565 TF. The real hazard is short kernels with large grids: at 8192 CTAs the same prologue costs 128µs flat, which would dominate an elementwise-scale kernel. Production backend should build CUtensorMaps host-side (cuTensorMapEncodeTiled + 128-byte grid-constant params, as the tutorials and Torch do) whenever the TileArray shape is known at launch — which for cuTile is always. For comparison, tileiras doesn't build tensormaps on device at all: its kernels contain no descriptor stores — the cubin carries EICOMPAT_ATTR_INST_TENSORMAP_V1 metadata and the r580+ driver constructs the CUtensorMaps at launch time from the kernel's own arguments (this is what the driver-version requirement buys), handing the kernel a ready buffer via a reserved constant slot (c[0x0][0x198]). Per CTA the kernel merely prefetches them (UTMACCTL.PF, ~2.3ns/CTA for 3 views, vs Triton's construct + tensormap.cp_fenceproxy + UTMACCTL.IV invalidate at ~5.3ns/CTA each). So cuTile-native already has driver-side "host" descriptors; a Julia launcher building CUtensorMaps via cuTensorMapEncodeTiled replicates the same design for the Triton backend in user space.
  • Cleanup noted: views created only for num_tiles probes currently emit a dead descriptor — at ~5ns/CTA that's ~1% on the 4096³ matmul; lazy or use-aware descriptor emission removes it.

Why this shape

Production consumers of Triton split three ways. TorchInductor generates Triton Python source and rides the stable tl.* API — wrong fit here, since cuTile.jl already sits on structured, canonicalized IR. JAX Pallas builds tt-dialect MLIR through native bindings and hands it to XLA's in-tree Triton — that is the Reactant path, explicitly not wanted. The remaining door is the wheel's IRSource: fully-specialized TTIR in, cubin/hsaco + metadata out. It is a niche but exercised, unit-tested upstream path, and the PoC confirms it works from text alone — Julia needs no MLIR C-API bindings for Triton's types beyond stock MLIR_jll with allowUnregisteredDialects.

Per-target status

CUDA Proven

Real cuTile kernels running on H100 at Python-Triton parity; native tileiras comparison available since cuTile 0.3.2 added Hopper (toolchain ≥ 13.3).

AMD Compiles

Same wheel, same TTIR → gfx942 hsaco. Needs validation on real ROCm hardware; AMDGPU.jl launcher is symmetric to the CUDA one.

CPU Open

No triton-cpu in official wheels (source-build only, lags upstream). Alternatives: microsoft/triton-shared (ttir→linalg, bring your own pipeline) or the existing MLIRKernels-style vector+OpenMP lowering as a non-Triton fallback.

Risks and mitigations

  • TTIR is not a stable format. No versioning guarantee; op attributes drift across minor releases. Mitigation: pin an exact wheel per package release; keep the emitted op surface small; version-gate the emitter.
  • No Julia-side verification with unregistered dialects — malformed IR surfaces as parse/verify errors inside triton.compile. Acceptable for machine-generated IR; a future Triton_jll (dialect + pass libs + C shim) upgrades to registered types, in-process verification, and a Python-free pipeline without changing any emitter code.
  • Printer/parser version skew. MLIR 18 → triton 3.7.1 worked; generic syntax has been stable since LLVM 17's properties change, but re-validate on every wheel bump (one smoke test covers it).
  • Python at compile time. Wheel-only, never at launch. The Triton_jll endgame removes it entirely if it becomes a problem.
  • Launch ABI drift. Trailing scratch parameters changed across 3.x. The generated PTX signature is ground truth; derive the launcher from it per pinned version.

Argument hints: the missing AssumeOp equivalent

Native cuTile feeds tileiras AssumeOp chains derived from ArraySpec; the Triton equivalent — tt.divisibility argument attributes feeding the AxisInfo vectorization analysis — was initially missing entirely, and every global access compiled to scalar LDG.E. The full mapping is now emitted: Alignment → divisibility on pointer args, ShapeDivBy → divisibility on size args (this one is load-bearing for masked loads: the mask offs < n only vectorizes when the bound is provably divisible, making the mask constant per 4-element group), StrideDivBy → divisibility on strides, and Contiguous → a compile-time constant 1 inner stride (attributes can't express "equals 1"; AxisInfo needs the literal — Python's equal-to-1 specialization, done statically). Result: LDG.E.128/STG.E.128 throughout, and fmha 87→289 TF, moe 17→52, batchmatmul 21→58.

One measured twist: on the tf32 matmul the same hints cost 30% (vectorized operand layouts perturb that kernel's tensor-core pipeline) while tripling batchmatmul — shape-dependent, so hint emission joined warp count as a second autotune dimension: dot-kernels race {hints, no-hints} × {4, 8 warps} once per specialization. Every kernel lands at its best configuration with zero manual tuning, and the full test suite is unchanged at 1,810 passes.

NegInf padding on TMA — built, measured, autotuned

The fmha blocker ("TMA can't fill −∞") is now solved generally: NegInf-padded loads on descriptor-eligible views lower to select(inbounds_mask, tma_load(view), −∞) — TMA zero-fill moves the data, register-only index math restores the semantics (the transformation hand-written Triton attention kernels apply). Descriptors were also extended from 2-D to CUtensorMap's full 2–5-D range, which fmha's 4-D 1×1×128×64 loads need. Verified against fmha's CPU reference. The measurement then overruled the hypothesis: 4-D descriptor loads run slower (240 TF) than divisibility-hinted vectorized pointer loads (291 TF) for this shape on Triton 3.7/sm90 — so load style joined the autotune race ({TMA, pointer}×{hints}×{4,8 warps}, deduplicated) and every kernel keeps its measured best. The remaining fmha gap to native (365) is tileiras' automatic warp specialization, not memory access.

What tileiras schedules, and closing the gap automatically

Reading EIATTR_REQNTID out of every natively-compiled example kernel: tileiras only ever picks 4, 8, or 12 warps — 4 for memory-bound kernels (our default already matches), 8 for single-tile tensor-core kernels (255 regs/thread on matmul and layernorm-fwd), and 12 (384 threads, a producer/consumer warp-specialization structure) with ~200 KB static shared memory for its deep-TMA-pipeline kernels (batchmatmul, moe, fft, layernorm-bwd). Notably, on several kernels where tileiras picks 8–12 warps, our 4-warp Triton builds still win — the warps serve its pipeline structure, not the workload per se.

Two mechanisms now close the schedule gap in the backend: a heuristic (kernels containing tt.dot default to 8 warps — fmha went 60→87 TF from this alone) and a first-launch autotuner mirroring @triton.autotune: for dot-kernels without atomics (rerun-safety), both 4- and 8-warp builds are compiled and raced once per specialization, the winner cached. Result: fmha keeps 87 TF (picks 8), matmul keeps 67 TF (picks 4 at these shapes), batchmatmul keeps 21 (picks 4) — no regressions from the heuristic anywhere. Upstream Triton itself ships no schedule estimator (defaults are literally num_warps=4, num_stages=3 dataclass constants; the in-tree perf model was removed with triton.ops) — choice lives in consumer-side formulas (TorchInductor) or measurement.

Upstream outlook

Research into triton-lang/triton (mid-2026) confirms our descriptor findings align with upstream direction — and that some of what we measured is unreported:

  • Upstream's answer to device-side descriptor cost is "don't": PR #4498 (by-value __grid_constant__ descriptors) explicitly rejected device-side creation over the same L2/fence costs we measured; PR #8786 (cheap in-kernel descriptor updates) was rejected in favor of ragged TMA (triton/tools/ragged_tma.py — one host descriptor + stride wraparound tricks). Host-side TensorDescriptor is the blessed path (tutorials converted in #6465, PyTorch standardized on it, launch overhead tuned in #7987).
  • Triton's launcher already does what NVIDIA's driver does — fill_tma_descriptor_tiled in the backend driver builds the CUtensorMap per launch from tensordesc_meta — but only for explicitly host-side descriptor kernel args. No pass auto-hoists device-side make_tensor_descriptor to the launcher. Our production plan (host-side unconditionally, since cuTile shapes are always launch-known) does for cuTile what no Triton frontend currently gets automatically.
  • The Tile IR convergence is real: the triton-lang/Triton-to-tile-IR incubator lowers Triton to NVIDIA's Tile IR, where tileiras decides host-vs-device descriptor placement automatically — the exact mechanism we reverse-engineered. Currently Blackwell-only (CUDA 13.1+); meetup notes say descriptor APIs are needed for perf today "but will be fixed in 13.2".
  • Our tf32-descriptor slowness appears unreported upstream (no issue matches; the official TMA tutorials are fp16/fp8-only, and issue #10229 shows device-side descriptor creation doesn't even survive the software pipeliner in some cases). Filing it would be a novel contribution.
